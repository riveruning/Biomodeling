## 已复现的问题

### F1 / P1：严格模式把明确数值失败归入未核验，Agent 因而仍可完成

使用声明非负的反应状态 x，x(0)=1，恒定消耗速率 0.4，求解到 t=4，得到 x=-0.6000000000000008。数值报告正确给出 `nonnegative=fail, severity=blocking`，但运行的 `scientific_status=not_verified`，Agent 最终 `state=completed`。

根因：`application.py:441–459` 在 strict 分支把 `not numeric_ok` 与来源未知、参考未通过统一降为 not_verified；`agent.py:602–615` 只检查模拟 succeeded 且 scientific_status 不为 failed。明确失败被未知状态掩盖。现有 `tests/test_research_workflows.py` 的相关测试手工构造 scientific_status=failed，没有覆盖“真实数值失败如何聚合成状态”这一步。

应当把执行成功、数值有效、参考匹配、来源支持、流程完成分开，统一生成裁决。硬失败不能被 unknown 覆盖；有效负结果可以正常归档，但不能复用当前含有“无明确科学失败”含义的 completed 状态。

### F2 / P1：数值属于谁、公式是否对应，缺少共同的证据绑定规则

来源 `Parameter k = 0.4; assay pH = 7.4.`，草稿却提交 k=7.4，引用整句，结果 ready。来源公式 `dx/dt = -k`，草稿改为 `k*x`，引用同一原文，仍 ready。

`agent_tools.py:130–138` 检查引文里有没有相同数字；表达式要求存在引用，但没有等价性或已确认转录的校验。`source_review.py` 主要检查材料之间的显式冲突；不存在材料自相矛盾，不表示草稿符合材料。

系统仍报告 semantic_support=unknown，因此没有伪造语义审核通过；问题是 reproduction 可执行门槛不能排除这类显式错配。建议先覆盖已支持的简单赋值和 ODE 语法，未知表达保持待审核，避免以更宽泛正则声称理解任意论文。

### F3 / P1：调用和结果尚未形成可恢复的持久事务

第一次 provider.respond 中断：已尝试 1 次调用，保存了 task，检查点和 agent_run 均为 0。模拟结果落盘后、返回 Agent 前中断：已尝试 2 次动作，科学 run 已保存 1 个，检查点和 agent_run 仍为 0。

`agent.py:360–363` 在内存里递增调用量后发请求；普通 submit/inspect/run 路径没有一致的调用前后保存。run_study 在执行前保存 run_count，做法不同。`resume_agent:212–223` 只接受正常保存的 awaiting_input。此限制文档已声明，本轮确认其具体后果。

需要调用记录、预算预留、稳定操作 ID、结果关联和恢复判定。网络请求发出后结果未知时，不能承诺 exactly-once，也不能直接自动重发。计算产物已经保存时应先认领结果；同一存储并发执行需要所有者锁/租约。ArtifactStore.recover 只修复对象索引，不恢复业务任务。

### F4 / P2：公开输入入口的校验不一致

`Parameter('k', True)` 得到 1.0，`Parameter('k', '0.4')` 得到 0.4；相同 JSON 经 from_dict 均抛 SchemaError。`contracts.py:130–138` 的 finite 直接 float()，而 serialization.py 的数值分支拒绝 bool/string。这影响 Python API 的契约一致性；当前 JSON/LLM 入口已拒绝，不能说它们也有此漏洞。

建议共同的严格数值验证用于构造器和 codec，历史序列化兼容单独处理，不把布尔值解释成实验参数。

## 代码和文档确认的结构性限制

1. **编排集中且规则重复。** agent.py 的 `_execute_agent` 同时负责请求、预算、工具参数校验、执行、事件、状态和 checkpoint；不同分支持久化策略已经不一致。按职责提取有实际收益，不以文件行数作为重写理由。
2. **研究入口尚未完全统一。** CLI hypothesis 直接调用 hypotheses.run_hypothesis_study；study-run/Agent 则经过冻结 plan 和 completion_eligible。旧内核末尾固定 status=completed，旧 CLI 仅按 failed 决定失败退出。应统一用例入口，并单列“无适合候选”和“所有计算均失败”。
3. **全研究超时并不成立。** 拟合在子进程限时，交叉核对另有模拟超时；hypotheses.py:171、197 的 predict 在调用进程执行 SciPy 积分，未受拟合 timeout_s 保护。这是代码确认的边界，未在本轮制造挂起案例。新增整任务 deadline 和每阶段耗时，而不是把每候选 timeout 宣称成总预算。
4. **材料解析仍只接 pypdf。** evidence.py 的 PDF 入口只提取逐页文本；尚无此前讨论的外部解析器适配、版面块、公式/表格和原页坐标映射。应接成熟解析输出并保留原文与转换版本，不自行实现 OCR。
5. **证据审核闭环未完成。** quote/offset 校验与 semantic_support 分离是优点；但当前 validate_links 始终返回 unknown，人工 review_status 也不等于完整语义支持流程。严格论文复现验收还需要有范围、有对象版本的审核决定及失效传播。
6. **RAG 结果还是开发证据。** passage_v2 的 19/21 对比 v1 的 10/21 来自 18 个合成开发案例，未独立审核。默认仍 v1；词汇不一致、长句裁剪、公式语义仍有限。不能据此宣布真实论文检索达到 90% 或直接证明 embedding 收益。
7. **成本/规模尚有限。** 工作上下文按字符限制，不是实际 token/费用上限；checkpoint 重复保存历史和请求，memory/cache 有全列表扫描。小规模可接受，先测规模曲线再做索引与事件拆分，不预设数据库迁移必要。
8. **版本与文档需收敛。** 产物哈希、环境指纹、resume_version、技能版本已经存在，但任务恢复尚不统一冻结所有工具实现/规则版本。README 是历史增量日志，v0.1 文档明确为历史说明，却混有读者可能当作当前限制的旧段落。当前架构、能力表、历史验收需有清楚入口。没有可用 Git 历史时，源码快照和差异可审计，但仅代码哈希不能恢复旧执行环境。
9. **评价证据仍不足。** 已有计算、故障和脚本流程验证，真实模型诊断样本小且对照底层模型/预算不同。先建立同模型、近预算、专家审核未见任务，再评价 Memory/RAG/Skill 增益。已见材料只能作开发回归。

## 局部架构目标

保留现有目录与接口，逐步增加内部边界：

```
CLI / Agent
    -> 共享用例与执行记录（任务、预算、调用 ID、阶段、恢复）
        -> 材料适配 / 检索 -> 结构化证据与审核 -> 草稿 / SBML
        -> 模拟 / 拟合 / 比较 -> 统一验证裁决
    -> 不可变产物和事实报告
```

LLM 决定有限动作；验证裁决和执行记录仍由确定性代码负责。证据记录保存“作者符号、内部目标、属性、数值/公式、单位、条件、来源位置、解析版本、审核状态”，与 ModelDraft 分离，复用现有 claim/source refs，不建立另一个可自由修改的执行真值。
