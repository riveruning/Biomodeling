# 研究查询读取优化（2026-10-31）

本轮改善研究工作台的项目面板、总览和报告查询，服务后续多案例开发试跑。单次查询反复核对同一引用图，导致 Windows 大量重复打开文件。先复用一次查询内已经核验的字节，再在成功返回前逐一重新读取、核对所有已观察文件；不建立跨请求缓存。

## 边界

- 全部哈希、对象结构、递归引用与深度检查继续执行；复用的是字节，不是“这个任务已成功”的结论。
- 原始字节缓存上限 8 MiB，按访问顺序淘汰。超限或已淘汰的数据仍保留最终核验责任。
- 成功返回前再校验文件，删除、同尺寸/时间戳篡改等会阻止返回。查询结束后视图不能再使用。
- 不创建目录或 SQLite/WAL，不使用索引决定预算。写入、模型请求、计算派发、确认范围与恢复继续使用原路径。
- 这不是原子文件系统快照；查询期间可能出现新记录。下一次查询重新读取，当前协议不承诺并发追加的事务快照。

## 当前测量

同一个两轮项目的面板状态、预算和数值摘要完全一致。下列读取数包含产物的字节读取与文本读取，源码指纹读取另计；每条耗时是本机单次诊断，不是严格压测或端到端加速比。

| 环境 | 原读取数 | 查询内复用后 | 原耗时 | 复用后 |
| --- | ---: | ---: | ---: | ---: |
| Linux，新源码同一存储 | 4713 | 1464 | 0.439 秒 | 0.272 秒 |
| Windows，既有运行版本同一存储 | 4209 | 1104 | 3.341 秒 | 1.231 秒 |

Windows 性能探针只读调用新查询辅助器，使用原运行包、原指纹及原记录，不改签旧对象、不重新计算科学结果。新源码与新存储的 Windows 接口检查另行执行。两个环境的样例存储内容不同，不能把两行直接当作操作系统性能比较。

仍有原生类型状态检查直接扫描 JSON 文本，源码指纹也继续按原规则检查；当前没有减少执行路径或规划循环的核验工作。存储继续随项目总数增长，百篇论文队列的实际速度尚未证明。

## 与科研主线的关系

这一步降低查看、核对多轮研究时的读取开销，不增加新的科学能力。五项研究流程中的对象/粒度、证据需求、假设选择与迭代仍由 Agent 提出；数值、来源、参考比较和具名讨论由现有协议留痕。实际文献中的粒度选择、证据充分性、数据映射和结果解读，仍需真实模型试跑后评价。

下一阶段优先小批公开开发论文：分别记录检索/提取、建模、计算、验证、讨论和 token 成本的失败分布；再决定扩展哪些建模路径及如何验证经验候选。独立评价集保持隔离，既有外部模型授权不扩大到新的论文案例。

本轮完整结果以 [查询优化验收](validation/20261031/query-read-performance.md) 为准。原 Windows 发布提交保留；本开发增量单独记录，验证后追加到现有运行分支与 PR #3，历史记录仍使用原版本。

扩展 Windows 检查发现既有上传路径会把 LF 自动改为 CRLF，导致 Emoji/中文来源的精确偏移错位。上传临时文件现按输入字符串的 UTF-8 字节写入；不替换换行、不归一化原文。原 Unicode 回归保持不变，另加 LF、CRLF 和混合换行逐字节检查。失败记录及修复后的完整结果分别保存。

完整 Windows 安装演练还发现了作业状态竞争：结束记录扫描为空后，内存状态恰好变成完成，会返回缺结果的完成状态。现先捕获活动状态，再扫描结束记录；没有已核对结束回执的内存完成保持未知。两个用例在修复前均稳定失败，修复后继续保留正常完成、重复查询和未知效果不重发的规则。

Windows 对拒绝 POST 的原路径还存在关闭连接时请求体未消费的问题。相同本机36请求对照中，修复前13次连接中止、23次403，修复后36次403、0次连接中止，两版业务写入均为0。拒绝判断与响应先发生，随后只丢弃长度唯一明确且不超过原大小上限的正文；清理采用0.25秒总截止和64KiB读取窗口，不解析正文、不创建作业。慢速或不完整正文不会无限延长清理。

真实浏览器还暴露了结论已形成、外层作业仍在保存回执时，导出按钮可以过早点击的界面竞争。界面现在跟踪已提交/排队/运行状态，结束回执确认前禁用导出；轮询先于POST确认响应处理完成时，也不再访问已删除的待办条目。未知效果保留原标识，不自动重发。Python全量通过后仅修改这一个JS资源，界面增量由专项接口和故意延迟回执的真实浏览器验证。
