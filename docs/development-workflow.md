# Codex 与 DSH 开发工作流 v0.1

本文件约束外部开发协作，不改变 BioModel Agent 产品内部的单 Agent 架构。

## 1. 分工与基本循环

Codex 负责任务拆分、科学语义与接口决定、权限监督、独立代码审查、测试执行和验收。DSH 负责在指定文件范围内实现代码和必要测试，并报告限制。DSH 的“完成”只表示提交了产物，不能代表 Codex 验收通过。

项目所有者已授权 Codex 自主处理项目目录内的开发与文件操作，并使用现有 DSH MCP/tool 辅助审批。常规读写、修复和验收不逐次向用户确认；任务文件范围由 Codex 管理，必要时由 Codex 审查并更新。

循环为：准备任务卡 → DSH 实现 → Codex 检查实际文件 → Codex 执行验收 → 接受或发送明确修复任务。一次只派发一个任务，不同时修改同一文件。

先验收环境与协作，再实现数据契约、表达式检查、SBML 构建、模拟、存储和研究工作流。不要把整个架构文档一次派给 DSH 要求全部实现。

## 2. 任务卡

机器可读任务卡放在 `tasks/`，格式参考 `tasks/workflow-smoke.json`。至少包含：

- 任务 ID、单一目标、允许阅读和修改的具体路径。
- 与本次有关的背景和接口约定；只提供必要上下文。
- 验收条件与 Codex 需要执行的检查。
- 超时和停滞预算。

默认一个任务只涉及一个行为、1–3 个生产文件及必要测试。超过 6 个修改文件应重新检查粒度。任务可以只交付分析，但要明确它不是实现任务。

DSH 优先直接读取列出的文件。当前网关支持明确路径的 read/write/edit；glob、目录扫描和一般 shell 执行可能无法通过策略。遇到工具问题应报告具体问题，不能换用未经审查的执行路径。

每次 `send_prompt` 会建立新会话，因此修复任务必须包含接口、失败证据和必要上下文。`preserveHistory` 不能恢复 DSH 的旧会话上下文。

## 3. 状态查询与 token 控制

使用 `scripts/dsh-workflow.mjs` 在后台监督一个任务。普通查询：`includeToolDetails=false`、`sinceLastRead=true`。不要把每次原始返回、完整工具历史或审计日志打印进主模型上下文。

- 无变化时按 2 → 5 → 10 → 15 秒退避；出现新工具请求或响应后重置。
- 新状态、审批事件和最终结果才打印短摘要；完整证据保存在本地日志。
- 权限申请仍带真实输入及策略证据；摘要化不降低审批标准。
- `sinceLastRead` 仅增量返回回答文本，不能对完整工具历史去重。
- 当前网关的 `wait` 最多约一秒，所以仅切换为 wait 不足以解决高频轮询。
- 后台轮询不重新发 DSH 提示词；DSH 自己的模型生成仍有独立成本。

Codex 等待监督进程时采用约 30 秒的等待间隔，每约一分钟向用户说明有意义的变化。无新信息时不反复读完整日志。准确 token/费用需供应商 usage；查询次数只作为开销代理指标。

## 4. 权限与验收边界

监督脚本仅在网关已明确判为 allow、证据完整且读写路径属于任务范围时调用 `review`。这仍是一次性审批，不开启 auto，不选 allow_always，不修改外部桥接器或权限策略。

unknown、waiting、deny、证据变更或超出任务范围均保存证据并结束本次任务。`needs_review` 表示需要 Codex 审查，不自动表示需要用户确认。对于已经授权的项目内操作，Codex 可调整任务范围或采用网关支持的工具重新派发；只有宿主或网关确实要求用户处理且无法在授权范围内解决时，才说明具体操作和拦截原因。不能用其他工具完成同一个被拒绝的操作来绕过限制。

网关的 `toolApprovalMode=manual` 是连接协议设置：Codex 通过 `approve_tool_call(action=review)` 调用辅助审批，由其规则判断是否允许一次执行，并非要求用户逐次点击。当前网关明确禁用 auto，因此不将其擅自改为 auto，也不修改用户原有审批配置。

依赖安装和测试由 Codex 在独立审查后使用自身受约束工具执行。监督脚本不运行任务卡中的测试命令，不把一般脚本自动批准给 DSH。

监督脚本及任务卡由 Codex 管理，不列入 DSH 可写路径。现有桥接器位于工作区外；本次只增加项目内的客户端工具，不修改桥接器。

## 5. 停滞与失败处理

默认：首次可观察活动预算 120 秒，活动间隔预算 180 秒，总预算 600 秒。这里的活动是新的文本或工具请求，不保证已有代码产出。此预算应大于提供方内部失败等待，避免内部还在盲重试、外层却只能显示 generating。

另设首个文件变更预算 300 秒，以及文件变更间隔预算 300 秒。反复输出计划或读取相同文件不能永久延长实现任务。任务可按复杂度在派发前调整预算。

到期时取消任务，保存已写文件和诊断；不删除部分产物，不声称任务完成。取消失败必须显式报告，并尝试关闭连接；不能开始另一个可能冲突的任务。

不自动反复重派提示词。Codex检查失败类型后最多做一次有实质改变的重试：工具问题改明确路径，任务过大改为单一文件，provider无响应先做短健康探测。健康探测失败就报告外部阻塞，不继续派发大任务。

## 6. 交付、审查与验收

DSH 结束时给出改动文件、实现接口、限制和建议测试。监督脚本核对实际文件是否新增/改变，列出缺失的期望文件；只有答案而没有文件的实现任务视为未交付。

Codex独立阅读改动，确认接口、科学语义和测试是否有区分力，然后执行适用检查。验收记录至少包含任务 ID、实际改动、运行命令、退出状态、关键数值证据、未覆盖项，以及 accepted / changes_requested / blocked 结论。

v0.1 实践中，重复小修复有时再次引入库接口或科学语义错误。Codex 可以直接修复已定位的验收问题并记录结果，避免为微小改动反复启动 DSH；主体实现仍按任务卡派发。直接修复同样须经过独立数值检查。

科学代码必须有数值或语义证据，例如解析解、非单位体积换算、缺参数拒绝、分段输入边界；不能仅凭“代码能导入”接受。工作流本身用离线模拟测试超时、退避、权限拒绝和无产物完成等路径。

## 7. 使用

```bash
node scripts/dsh-workflow.mjs --task tasks/workflow-smoke.json --dry-run
node scripts/tests/dsh-supervisor.test.mjs
node scripts/tests/dsh-runtime.test.mjs
node scripts/dsh-workflow.mjs --task tasks/workflow-smoke.json --bridge-root /home/riveruning/tools/mcp-acp-bridge
```

第三条会启动独立的 MCP 桥接进程和新 DSH 会话，不能接管工具连接 `biomodel-v01`。应先结束旧任务。脚本复用现有桥接器中的 MCP SDK，不安装新的依赖。执行仍受宿主文件、进程和网络权限约束。

本项目的开发后端选择保存在 `config/development-runtime.json`：当前为 USTC 的 qwen3.8-chat + openai-completions。可使用 `--model` / `--provider-api` 做单次覆盖。它是 DSH 的模型后端，不是 BioModel Agent 产品模型选择，也不更改用户全局 DSH 配置。

每次启动在工作区外的随机临时目录创建受限运行覆盖层，完整保留原提供方配置和凭证引用，覆盖模型、协议、超时/重试，并移除本任务不需要的 shell、搜索、联网、待办和子 Agent 工具：流式空闲 60 秒、请求超时 75 秒、内部重试 0 次。仍使用原 MCP 桥接器、原固定 DSH 程序和原权限门控。退出后删除本次临时控制目录；不复制实际 API 密钥，不改宿主配置。默认模型是本轮实测可工作的开发选择，不代表科学能力评测结果。

若 DSH 会先读新目标文件，Codex 可在授权项目目录内准备空源文件并明确告知 DSH；主体代码由 DSH 实现，Codex 可以在验收中直接修正已定位的问题；修正理由和验证结果留档。空文件不算交付。不要为了读取不存在的文件扩大权限，也不要把每个可通过任务准备解决的问题交给用户。

当前 Codex 沙箱实测禁止 Node 子进程启动（EPERM）。因此真实协作需通过宿主允许的执行方式启动；这与 DSH 工具的一次性文件审批是两层不同限制。不能以关闭 DSH 网关来解决宿主限制。离线测试可以直接执行测试文件：`node scripts/tests/dsh-supervisor.test.mjs`；某些受限环境的 `node --test` 只展示文件级汇总，直接执行会显示各项结果。

输出目录为 `.workflow/runs/`。终态摘要写入 `summary.json`，审计写入 `audit.jsonl`，DSH回答写入 `response.txt`；这些文件不提交版本库。输出中不报告“验收通过”，只报告交付与监督状态。

## 8. 环境隔离约定

所有项目 Python 依赖安装到 `/home/riveruning/biologymodel_agent/.venv`，测试和运行使用显式的 `.venv/bin/python`。不激活或修改 conda base，不执行全局 pip/conda 安装，不改变 shell 启动文件、全局 PATH、原有 Node/MCP/DSH 安装或其他项目环境。

当前 `.venv` 基于 `/usr/bin/python3.12`，`include-system-site-packages=false`。首次安装用系统 pip 的 `--python .venv` 指定安装目标；依赖写入项目 `.venv`，不写入系统或 conda base。后续安装优先 `.venv/bin/python -m pip`。

提供方诊断脚本 `scripts/dsh-provider-probe.py` 只读使用宿主已有的 PyYAML，不安装包。运行它时用 `/usr/bin/python3`，以避免当前 shell 激活环境改变解释器。它只向已配置的 USTC 地址发送最小诊断请求，不输出凭证；正常科学计算和测试仍只用项目 `.venv`。

首次创建 venv 因缺 ensurepip 未成功；现已在原项目目录完成独立环境，不安装系统 python-venv 包来改变宿主。2026-10-14 已核对 numpy、scipy、libSBML、libRoadRunner、pytest 均从项目 `.venv` 加载。

DSH 若需要新依赖，应在交付说明列出，由 Codex 在项目环境中安装。原有环境只做必要只读检查，不为本项目升级或重装。缓存和运行产物尽量留在项目目录；只读复用已有工具，不将其当作可随意修改的项目文件。
