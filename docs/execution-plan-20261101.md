### BUG-01：研究循环与正式模型适配器的返回结构不一致

- 位置：[`llm.py`](../src/biomodel_agent/llm.py) 的 `ChatProvider._parse`，基线第 324 行；[`research_supervisor.py`](../src/biomodel_agent/research_supervisor.py) 基线第 198 行；[`research_projects.py`](../src/biomodel_agent/research_projects.py) 的 `_operate_owned` 回答绑定检查。
- 模拟 HTTP 返回合法的 `{"action":"scenario_source","args":{}}`。正式适配器将它变为含 `reason: ""` 的三个字段。
- 研究循环严格检查仅两个字段，记录 `invalid_response`。1 次调用预算耗尽，来源创建数为 0。
- 对照：直接返回同一动作的两个字段的 Scripted provider 可以成功创建 1 个来源。
- 这解释了为什么脚本演练可成功，正式适配器组合仍有阻塞。复现没有联系真实模型，无法据此评价模型智能。

**修复任务 FIX-01（已实施）**

- 目标：在研究入口明确归一化动作，保留原始回答及理由，同时使动作验证和保存回答的绑定检查使用同一契约。
- 允许修改范围：`research_supervisor.py`、`research_projects.py`；必要时增加小型共享响应契约模块；对应研究项目测试。
- 不要只把 `reason` 加入第 198 行的可选字段：后面的回答全对象比较也会失败。也不要全局删除 `ChatProvider` 的理由字段，避免破坏旧 Agent 契约。
- 验收：通过 `httpx.MockTransport` 使用真实 `ChatProvider.respond`，覆盖模型省略 reason、空 reason、非空 reason；来源动作和合法结束动作实际生效；未知字段仍拒绝；篡改 action/args 不能通过绑定；保存回答的认领与恢复不重复请求。
- 完成条件：新增测试在旧实现上能失败，在修复后通过；原研究项目/任务建议/恢复测试通过；保存旧失败记录。
- 估算：0.5–1.5 人日。

### BUG-02：经验提取要求的结构不属于默认 provider 协议

- 位置：[`research_pipeline.py`](../src/biomodel_agent/research_pipeline.py) 的 `lessons`，基线第 180、185、190 行；[`llm.py`](../src/biomodel_agent/llm.py) 第 310–315 行；CLI 使用 `research_cli._provider` 构造该适配器。
- 给出符合经验提取提示的 `{lessons:[...]}` HTTP 回答，正式适配器抛出 `ModelResponseError: model response has unknown key(s) ['lessons']`。
- 实际留下 1 条 lesson attempt、0 条 lesson response、0 个经验候选。重复调用被未知结果保护阻断，并未再次请求。
- 这是确定的契约冲突。禁止未知效果重试本身不是 bug；需要修好调用协议，并给已存在错误记录清晰的诊断/后续处理方式。

**修复任务 FIX-02（已实施）**

- 目标：让经验提取使用明确的响应协议。优先与当前适配器一致，采用如 `action=propose_lessons, args={lessons:[...]}` 的固定信封，并校验动作名和候选内容。
- 允许修改范围：`research_pipeline.py`，必要的 CLI 接口说明，`tests/test_research_pipeline.py`。
- 验收：真实 ChatProvider + MockTransport 能产生候选；错误 action、错误 case_id、格式错误被拒绝；候选保持 inactive；重复消费已确认回答不产生新外部请求；旧结构兼容或明确版本拒绝，不能静默重解释旧收据。
- 调用解析失败与外部结果未知需分别诊断，不能通过删除预留、重置额度来“修复”。
- 依赖：与 FIX-01 对齐响应规范；生产文件可独立修改。
- 估算：0.5–1 人日。

### BUG-03：前端预算判断掩盖可执行的已保存回答

### INT-01：避免再次只测脚本返回

- Scripted provider 继续用于科学状态和故障控制，但每个公开入口至少补一条真实 `ChatProvider` + MockTransport 的贯通检查。
- 覆盖 `research-project-run`、工作台 `run_project`、`research-batch-run` 和 `research-batch-lessons` 的正式配置路径。
- 必须证明动作真正执行、证据/结果落盘、报告匹配；HTTP 200、作业 returned 或测试桩收到请求都不足以代表完成。
- 断言请求数、用途和预算；保留无真实 API key、无外部网络的常规回归方式。

### EVAL-01 / EVAL-02：具体评测安排

- 建议首批 4–6 个 ODE、1–2 个 Boolean/SSA、1 个已有 FBA 输入，最终控制在 6–10 个案例；至少覆盖三个机制家庭。
- 每案登记材料版本、授权范围、任务模式、预期缺口、明确不支持项、参考来源与独立性。明确声明、论文原文和缺失/冲突控制分开统计。
- 先冻结输入、实现、模型服务与额度，再运行；第一次失败和后续修复重跑分列。不要据同论文的多个条件夸大独立论文数量。
- 报告至少包含：解析是否足够、输入构建是否成功、数值是否通过、来源是否可核查、参考是否匹配、人工干预次数、停止原因、耗时、已知 token 和未知 usage。
- 本轮使用开发资料，不读取独立评价集来指导修复；领域审核作为独立状态，不由 Agent 自签。
- 决策门：只有出现稳定高频阻塞后，才确定 DATA-01 和 SCI-01 的具体题目。若主要问题仍是动作协议或状态流，先修工程，再扩展解析功能。

### CAP-01：最小能力表

- 不先把 ODE/FBA/typed 重写成同一求解框架。统一的是能力描述与查询入口。
- 字段至少包括模型类型、profile、研究模式、输入格式、来源草稿支持、参考比较类型、恢复版本、外部工具与已知限制。
- CLI、任务建议、研究提示和工作台逐步引用同一目录；数值检查权仍在原后端。
- 验收：声明“支持”的组合有正向集成控制；声明“不支持”的组合返回一致、可理解的原因。

### DATA-01 / UI-01：按失败分布选择一个切口

- 如果首要问题为 PDF 公式：保存区域、原图和候选表达式，支持核对后采用；不把 OCR 置信度当科学证据。
- 如果首要问题为数据表：选择列、单位、条件与观测映射，保留原始单元格和转换记录。
- 如果首要问题为显式声明语法：支持有证据的常见表达并添加歧义负控制，不以放宽所有绑定解决。
- UI 交付以一个真实案例端到端为准；第一批只做适配该案例的图形，不能自动补未知数据。

### RUN-01 / SCI-01 / REL-01：稳定性与可信度

- RUN-01 分两个小提交：先统一只读用量与时间视图，再做期限/停止状态；已保存结果不丢失，缺失 token 不写 0，未知效果不自动重试。
- SCI-01 只选一个类型：SSA 可从冻结的分布/矩指标入手；PDE 可从网格收敛与解析参考入手；Boolean/个体按其观测和干预语义定义指标。固定统计方法、随机种子策略和阈值后再执行。
- REL-01 保留现有全量回归，在此基础上增加跨系统最小安装、中文路径/换行、运行与导出检查；不要为了缩短 CI 删除科学负控制。
