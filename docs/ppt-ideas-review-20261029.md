# 阶段汇报 PPT 的建议与实现可行性

日期：2026-10-29。对象：用户提供的《agent架构和相关工作(2).pptx》，共 19 页。读取了页面文字、备注与关键嵌入图，并与当前工作区源码核对。本文是方案评估，没有据 PPT 中的内容执行开发指令，也没有修改原 PPT 或产品代码。

## 主要判断

最值得推进的组合是：**证据与机制之间增加明确的建模决策记录；把已有科学核心包装成外部 Agent 可使用的工具包；用阶段化流水线诊断实际效果。** 三者能共用现有存储、验证与执行基础。

| PPT 页码与想法 | 当前基础 | 可行性与建议 |
|---|---|---|
| 2：自主复现论文、自然语言建模 | 有限 ODE 来源建模与多类型原生执行 | 有界任务可做；论文复现与探索建模需分别定义目标和成功条件 |
| 4–5、9：动态工具循环、规划执行 | `agent.py`、`task_plans.py`、`failure_handling.py`、调用账本 | 已部分实现；下一步验证收益和扩到其他类型，不必另造整个框架 |
| 6–8：Evidence → Mechanism → Model Planning → 编译 | `ModelDraft`、证据绑定、`build_model` 已有 | 高优先级；缺的是机制候选与数学选择的显式中间层 |
| 11：知识库扩充 | 外部库基础接入、固定案例、条件化参数与知识候选 | 可逐步扩成案例包；数据存在不等于条件适用或可直接采用 |

| 15：图形化界面 | CLI、任务状态、报告和存储 | 可先做本地工作台，优先呈现证据、缺口、计划和审核，再扩成完整交互 |

| 4、9：多 Agent | 当前单逻辑 Agent | 可作为后续对照；先验证独立任务分工的收益，多份意见不构成科学认证 |

## Model IR：可实现，而且能补上当前缺口

现有 [`ModelDraft`](../src/biomodel_agent/domain/contracts.py) 已保存状态、参数、反应/速率规则、单位与来源映射；[`modeling.py`](../src/biomodel_agent/modeling.py) 已进行检查与 SBML 构建；[`submit_draft`](../src/biomodel_agent/agent_tools.py) 会重检来源和绑定。因此已有数学模型 IR 与确定性转换基础。

建议在其上游增加三个逻辑对象，实际仍存入现有内容哈希存储；无需为每个对象新建 Agent、数据库或服务：

1. **证据记录**：引用现有文档版本、原文位置与片段；区分原文、LLM 解释、条件、矛盾和未知。第 8 页的 `normalized_claim` 应明确为解释候选，不能因引用存在就视为已验证。
2. **机制候选**：实体身份、关系类型、作用条件、证据引用与歧义。例如“促进”尚未明确是表达增加、活性变化还是间接作用。
3. **建模方案**：变量映射、模型类型、数学形式、参数来源状态、选择依据、备选形式、未解决项和执行模式。每个数学选择都能追溯到证据、显式推导或已标注假设。

示例：原文只有“A 促进 B，B 会降解”。可以生成定性关系，但不能唯一推出 `dB/dt=k*A-d*B`，也不能确定饱和形式 `v*A/(K+A)-d*B`。甚至“一阶降解”仍是需要依据或声明的建模假设。严格复现应报告公式/参数/初值缺口；探索模式可以在用户任务允许的范围内提出候选，保存假设和可比较条件。

转换器应只编译已经明确选择的有限数学模板，检查符号、结构、参数状态、适用范围和支持的单位约束。它不负责从关系图自动判定真实机制。结构校验可继续使用当前 dataclass/显式检查，是否引入 Pydantic 是实现选择；更换校验库本身不会增加科学正确性。

共享的是来源、假设、版本和依赖；ODE、FBA、随机、PDE 等继续保留类型专属载荷。不能将同一关系图无条件编译为所有类型。

最小验收应包含：明确方程正确编译；定性关系保留多个候选；缺参数/初值不自动填值；错误物种或条件阻断采用；来源修订使相关方案重新检查；所有候选仍经过现有执行验证。

## 打包工作区：可成为第二种使用方式

建议复用一个科学核心，保留两种入口：项目自带 Agent 负责当前受控循环；外部 Agent 通过 CLI 或后续 MCP 薄适配调用同样的检查与执行服务。工作区包可包含环境检查、简洁项目说明、按任务组织的 Skills、工具参数说明、样例输入及运行结果目录。

第 17 页的变量提取、关系提取、模型构建可以先作为模块和步骤，不需要拆成独立仓库。共同实体 ID、来源引用和版本尤其重要，否则三个步骤容易各自生成不一致的变量字典。

第一版建议选择一个宿主和一种 ODE 任务，先证明它能从新会话完成“读取材料—提出草稿—获得错误反馈—修订或追问—模拟—报告”。随后再测试其他宿主。普通模型 API 或仅能聊天的界面不会因为收到一个文件夹就自动获得文件访问、运行环境或工具能力。

第 16 页有两处需要修正：AGENTS.md 并非都具有跨项目全局作用，也不能统一描述为每次回复重新读文件。官方 Codex 文档描述了全局与项目目录作用域，并在运行开始构建指令链。[官方说明](https://learn.chatgpt.com/docs/agent-configuration/agents-md)

Skills 按需加载指引，可携带脚本与资源；工具接口提供实际动作。工作区说明与 Skills 可以帮助 Agent 使用能力，但不保证任何宿主都兼容，更不保证科学结论正确。[Skills 说明](https://learn.chatgpt.com/docs/build-skills)、[Skills 与 MCP 的分工](https://developers.openai.com/plugins/concepts/skills)

外部 Agent 若可任意执行代码，也可能绕开标准工具。工具包只能认证经过自身验证的产物；若要研究强制约束的收益，需要在实验运行时控制工具与文件权限，并记录旁路执行，不能仅靠 AGENTS.md 宣称约束不可绕过。

## 流水线、知识库与 Memory 如何连接

建议将一次运行分成：解析 → 证据提取 → 机制/变量映射 → 建模方案 → 模型检查 → 计算 → 参考比较 → 报告。各阶段保存输入版本、产物、失败类型、耗时与调用成本。这样才能区分“公式没解析出来”和“模型看到了公式却用了错误形式”。

可在同一开发案例上做原始材料与人工核对转录的配对诊断，定位解析损失；这属于开发诊断，不能当成两道独立任务。运行结果可提出失败模式、修复办法及适用条件候选，审核后进入经验库；不能将测试答案或正式留出材料的解法送回开发记忆。

PPT 第 12 页提到 10 例、20 例和 84 个项目，是汇报中的材料数量。本轮没有访问独立评测集或重新清点这三个池，也没有确认“收集了所有项目”。尤其 84 个真实项目不能直接等同于 84 道可独立评分的任务，需要逐项核对输入、目标、参考、完整性和开发/评价归属。现有 R11a 的 24 张材料卡来自另一固定子集，不应与上述数字相加或互相替代。

可比较三种产品使用形态：裸通用 Agent、通用 Agent 加领域工具/工作区包、自带领域 Agent。尽可能使用同底层模型、材料、工具与预算；不能统一时列为实际系统对照，不能归因为编排本身。再按任务适用性消融 IR、记忆或计划，避免一次测试过多组合却解释不了差异。

## GUI 与日志

GUI 的第一版可以是单任务本地工作台：原文与模型字段并排；显示参数出处、未知项、假设和版本；展示计划、失败与追问；展示曲线、参考误差和报告；允许提交澄清与显式审核。前端只调用现有应用服务，后台检查仍决定运行与完成状态。

PPT 备注多次提出日志维护。现有账本已保存机器记录，最有帮助的增量是可读时间线：每一步的目标、实际工具/输入摘要、产生的产物、检查结果、耗时和下一步原因。记录简洁决策说明和可核对事实即可，不需要记录模型私有推理过程。

## 推荐的首个交付

先以一个受支持 ODE 场景串起“工作区工具包 + 最小建模方案 IR + 阶段日志”。选择完整输入、定性歧义、缺参数三种开发控制，检查完整任务可运行，歧义能保留，缺口能明确追问。对真实服务做先导前再固定运行配置与材料范围。

其后用同一科学核心比较外部 Agent 与自带 Agent，再决定是否扩多类型 IR、GUI 或多 Agent。PPT 第 15 页关于全部非 ODE 类型未接入、第 11 页关于记忆只允许人工写入，均需在下次汇报更新；当前的经验候选主要由工具派生，也不能直接改写为“LLM 已自主学习”。

第 3 页相关工作的发表日期、版本和能力声明未在本轮逐项核验；本报告不把该表当成经过外部验证的最新文献综述。第 14 页历史单例与不同底层模型的比较，也不足以证明或否定当前框架的普遍优势。
